# GitLance — rules for agents

What GitLance is and what it does: `README.md`.
Feature specs, UI mockups and design decisions: the sibling repo `../Design` — a new feature starts there.

- **Everything written here is English** — code, comments, docs, commits.
- **Rust, stable toolchain.** `cargo fmt` and `cargo clippy --all-targets -- -D warnings` clean (as CI runs it: without
  `--all-targets` the tests' lints go unseen), `cargo test` green before a commit to `main`.
- **UI first.** GitLance is the app; the binary takes at most an optional repository path, or one of the two
  windowless modes an agent runs (`mcp`, `agent-watch` — Agents below). A real CLI is outside scope — ask first.
- **Read-only towards the reviewed repository.** GitLance reads git state and never changes the index, the
  working tree, refs or reflogs; it writes nothing there. Comments for an agent are kept in its application support directory, and agents read and answer them through its MCP server (Agents below). The named exceptions: the background fetch (on until turned off, per repository) (`ui/fetch.rs`, the `git` CLI) writes remote-tracking refs and objects; opening a merge request whose branch is not here (merged and deleted, closed, a fork's) fetches its head once to `refs/gitlance/requests/<n>` (`fetch::fetch_request`, #114), a namespace no remote's `--prune` touches, read as a `RefKind::Request` branch that no list or search shows; a request whose base or head as its host compares it is not here fetches its target branch to its remote-tracking ref, or its head as above (by the commit when GitLab deleted the ref), once (`fetch::fetch_branch`, `fetch_request`, #145); and a comment the user posts to a merge request with ⌘↵ (`mr::post_discussion`) goes to GitLab, not to the repository. Comments for an agent (purple) stay on the Mac; comments on a merge request (orange) are public. A feature that would
  stage or commit is outside scope — ask first.
- **No worktrees, no checkouts.** Branch and range diffs are read from objects, not from a second working tree.
- **GPUI is pre-1.0.** Pin it to an exact version (or Zed commit) in `Cargo.toml`; an upgrade is its own
  change. It builds with `runtime_shaders`, so full Xcode is not needed.
- **Colours come from a theme** (#12): One Dark is the default of five built-in themes (`assets/themes/*.json`, from Design `design/system/themes.css`); a user's themes are the `.json` files in the data folder's `themes/`. Draw only with `ui::theme` functions (each reads a token of the theme in use) and code with `theme::code(role)` — never a colour literal. Every built-in's text tokens must read at 4.5:1 on every surface (a unit test checks it).
- **Checking the UI** needs no screen access: `GITLANCE_SNAPSHOT=<file.png> cargo run --features snapshot -- <repo>`
  renders the window offscreen to a PNG and quits, without taking focus. `GITLANCE_SNAPSHOT_VIEW=unified,lines,words,structural,underlined,wrap,all-lines,whitespace,one-file,settings,settings-general,settings-repository,keyboard,agents,send,swipe,onion,menu,notice,comments,viewmenu,linemenu,tool-discussions,tool-agents` (`settings-general`, `settings-repository`: Settings at that section; `keyboard`: Settings → Keyboard with its filter taking the keys; `tool-<name>`: that tool window open)
  turns view options (or the Settings page) on, unsaved; `GITLANCE_SNAPSHOT_SEARCH=<text>` fills the commit search and `GITLANCE_SNAPSHOT_FIND=<text>` the find bar of the diff; `GITLANCE_SNAPSHOT_KEYS="right cmd-t"` sends keystrokes to the window (not the keyboard) (`wait` pauses a second for a diff to load); `GITLANCE_SNAPSHOT_OPEN=<path>` opens another repository as ⌘O would (the this tab / new tab card asks), `GITLANCE_SNAPSHOT_COMPARE=<base>,<head>` shows a comparison, `GITLANCE_SNAPSHOT_PALETTE=<text>` opens the ⌘K palette (`compare:<text>` the compare picker); `GITLANCE_SNAPSHOT_VERSIONS=1` (with VIEW `interdiff`: the first modified commit pair) compares the first and last versions; `GITLANCE_SNAPSHOT_MENU=open-in` opens Open in's ▾ on the page the keys reached; `GITLANCE_SNAPSHOT_LIST=<px>` sets the width of the Inbox's, Branches' and Merge requests' lists, to see their rows narrow.
  Never drive the real mouse or keyboard for a check: the developer is using the machine.
- **macOS, Windows and Linux alike.** What differs per OS (data folder, icon, editor launchers, title bar, which apps open a file — `apps_for`, `open_with`, `preview`, #78) lives in `src/platform/` (`macos.rs`, `windows.rs`, `linux.rs`); nothing else uses `cfg(target_os)`. Shipped keys are written the macOS way (`cmd-o`, `⌘O`): `platform::keys` binds them as Ctrl on Windows and Linux (⌘1…9 → Alt+1…9), a primary-modifier check is `Modifiers::secondary()`, and every shortcut shown goes through `keys::text` or `keys::caps`, which spell it `Ctrl+O` there. CI (`.github/workflows/ci.yml`) runs clippy and the tests on all three; a `release/v*` tag runs `release.yml` (README → Releases (for maintainers)) — ask before tagging. A release's notes are its `## <version> — <date>` section of `CHANGELOG.md` (what is new, for someone using the app), then its commits by kind (`.github/release-notes.sh`, #135): a change worth telling goes under `## Unreleased`, renamed to the version when it is released; a tag without its section fails. A released version's section changed is written to its release at once — the developer, 2026-10-26: the notes must read the same in each release's description on GitHub — `.github/release-notes.sh <version>` as the body of a PATCH to the release (the GitHub token has Contents: write), or `release-notes.yml` (by hand).
