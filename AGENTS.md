# GitLance — rules for agents

What GitLance is and the MVP: `README.md`.
Feature specs, UI mockups and design decisions: the sibling repo `../Design` — a new feature starts there.

- **Everything written here is English** — code, comments, docs, commits.
- **Rust, stable toolchain.** `cargo fmt` and `cargo clippy -- -D warnings` clean, `cargo test` green before
  a commit to `main`.
- **UI first.** GitLance is the app; the binary takes at most an optional repository path. A real CLI is
  outside the MVP — ask first.
- **Read-only towards the reviewed repository.** GitLance reads git state and never changes the index, the
  working tree, refs or reflogs; it writes nothing there. Review comments are kept in its application support directory and copied to the clipboard; a `.misc/review.md` file or an MCP server for agents is a later, separate decision. The named exceptions: the opt-in background fetch (`ui/fetch.rs`, the `git` CLI) writes remote-tracking refs and objects; and a comment the user posts to a merge request with ⌘↵ (`mr::post_discussion`) goes to GitLab, not to the repository. Comments for an agent (purple) stay on the Mac; comments on a merge request (orange) are public. A feature that would
  stage or commit is outside scope — ask first.
- **No worktrees, no checkouts.** Branch and range diffs are read from objects, not from a second working tree.
- **GPUI is pre-1.0.** Pin it to an exact version (or Zed commit) in `Cargo.toml`; an upgrade is its own
  change. It builds with `runtime_shaders`, so full Xcode is not needed.
- **Colours come from a theme** (#12): One Dark is the default of five built-in themes (`assets/themes/*.json`, from Design `design/system/themes.css`); a user's themes are the `.json` files in the data folder's `themes/`. Draw only with `ui::theme` functions (each reads a token of the theme in use) and code with `theme::code(role)` — never a colour literal. Every built-in's text tokens must read at 4.5:1 on every surface (a unit test checks it).
- **Checking the UI** needs no screen access: `GITLANCE_SNAPSHOT=<file.png> cargo run --features snapshot -- <repo>`
  renders the window offscreen to a PNG and quits, without taking focus. `GITLANCE_SNAPSHOT_VIEW=unified,lines,words,structural,underlined,wrap,all-lines,whitespace,one-file,settings,keyboard,agents,send,swipe,onion,menu,notice,comments,viewmenu,linemenu,tool-discussions,tool-agents,tool-notifications` (`keyboard`: Settings → Keyboard with its filter taking the keys; `tool-<name>`: that tool window open)
  turns view options (or the Settings page) on, unsaved; `GITLANCE_SNAPSHOT_SEARCH=<text>` fills the commit search and `GITLANCE_SNAPSHOT_FIND=<text>` the find bar of the diff; `GITLANCE_SNAPSHOT_KEYS="right cmd-t"` sends keystrokes to the window (not the keyboard) (`wait` pauses a second for a diff to load); `GITLANCE_SNAPSHOT_OPEN=<path>` opens another repository as ⌘O would (the this tab / new tab card asks), `GITLANCE_SNAPSHOT_COMPARE=<base>,<head>` shows a comparison, `GITLANCE_SNAPSHOT_PALETTE=<text>` opens the ⌘K palette (`compare:<text>` the compare picker); `GITLANCE_SNAPSHOT_VERSIONS=1` (with VIEW `interdiff`: the first modified commit pair) compares the first and last versions.
  Never drive the real mouse or keyboard for a check: the developer is using the machine.
- **macOS first, Windows and Linux built too.** What differs per OS (data folder, icon, editor launchers, title bar) lives in `src/platform/` (`macos.rs`, `windows.rs`, `linux.rs`); nothing else uses `cfg(target_os)`. Shipped keys are written the macOS way (`cmd-o`, `⌘O`): `platform::keys` binds them as Ctrl on Windows and Linux (⌘1…9 → Alt+1…9), a primary-modifier check is `Modifiers::secondary()`, and every shortcut shown goes through `keys::text` or `keys::caps`, which spell it `Ctrl+O` there. CI (`.github/workflows/ci.yml`) runs clippy and the tests on all three; a `release/v*` tag runs `release.yml` (README → Releases) — ask before tagging.

- **Agents** (`src/agents.rs`, `src/mcp.rs`, `src/watch.rs`, `src/ui/agent.rs`): the binary has two modes an agent runs, no window — `GitLance mcp` (an MCP server on stdio: `list_comments`, `address_comment`, `reply_comment`; its `instructions` tell the agent to start the watcher) and `GitLance agent-watch` (run in the background from a chat; it finds the chat from `CLAUDE_CODE_SESSION_ID` / `CLAUDE_PID`, says it listens in `agents/chats/`, and prints one line and exits when comments are sent to it, which wakes the agent). Purple comments are drafts (the composer's Add to drafts ⌘↵; Send all ⇧⌘↵ and Send this only ⌥⌘↵ beside it, #50 F) until sent: to the chat they usually go to (the last one while it listens, else any listening; `send_agent`), or the card (⇧⌘A, Choose the chat…) picks one; ⇥ in a GitLab / GitHub reply makes it a purple note on that discussion, kept on this Mac with the discussion for the agent (`Comment::thread`, #50 G); the agent may ask back with a form (`reply_comment` `form`: one, many, confirm, plan, code, files, text, order, scale, line — `review::Form`), answered in the card with clicks, Your call or a note (`Comment::answer`, back to the drafts, in the next brief, #10 C); the Agents window groups Drafts · Asks you · Sent · Addressed · Sent back · Resolved; snapshot VIEW `agent-form`; the agents' answers go to `agents/answers/<repo>.jsonl` and the app applies them (each once, by uid; only the app writes the comments). States: draft → sent → addressed (the agent) → resolved (the reviewer; Reopen sends it back to draft). Settings → Agents runs `claude mcp add -s user` for every `~/.claude*` profile. Snapshot views `send` and `agents`; test the loop with `HOME=<dir>` so the real data folder is untouched.
